# DDD 建模示例：领域词汇、子域划分与 ADR

> 本文是 `任务聚合Kanban系统-DDD领域设计-v0.2.md` 的教学示例，不新增领域事实，也不替所有者关闭待决 ADR。
> 同一场景贯穿三个练习：先统一语言，再按变化原因划子域，最后把取舍写成可追溯决策。

## 1. 贯穿示例：两次“产品使用复盘”

- **R1**：11 月 18 日复盘新用户首次使用，目标是形成可复现的问题清单；实际执行 68 分钟，结果为“识别 4 个首次使用阻碍”。
- **R2**：11 月 25 日复盘企业客户续约访谈，目标是形成可与客户确认的风险清单；实际执行 86 分钟，结果为“形成 3 项续约风险，其中 2 项已有访谈证据”。
- 人比较两次真实工作后，确认它们属于同一类工作，创建 TaskTemplate“产品使用复盘”，并分别关联 R1、R2。
- R2 与“整理企业客户续约访谈”“补充客户访谈证据引用”组成 TaskSet，并在具有名称和当前目的后承担 ExecutionPlan 角色。

这里最重要的判断是：**同类不等于同一次，同组不等于父子任务，完成不等于目的达成。**

## 2. 领域词汇表示例

### 2.1 基本对象

| 通用语言 | 定义 | 本例 | 不要混成 |
|---|---|---|---|
| **TaskInstance（任务实例）** | 某一次真实发生、拥有稳定身份的工作 | R1、R2 各有独立 `task/id` | 模板、任务标题、重复执行次数 |
| **TaskTemplate（类任务）** | 至少两个实例经人确认后形成的可复用规约 | “产品使用复盘” | 可直接开始或完成的 Todo |
| **TaskBackground（实例背景）** | 这一次工作的约束、资源、标的信息、期望结果与观测口径 | R2 的访谈对象、证据要求、风险属性 | 模板默认背景的实时引用 |
| **ExecutionSegment（执行段）** | 某实例一段有起止时间的实际执行；活跃段的结束时间为空 | R2 的 09:12–09:48 | 暂停本身、自然时间跨度、一次新实例 |
| **TaskResult（实际结果）** | 对某实例实际观察到的结果快照，区分观察与录入时间 | R2 的 3 项风险及证据引用 | 期望结果、完成状态、目的达成结论 |
| **TaskRelation（时序关系）** | 两个实例之间的 `precedes` 关系 | “整理访谈”先于 R2 | 自动阻塞、父子关系、执行历史 |
| **TaskSet（任务集）** | 使用者把若干平级实例视为一组的组合 | “企业客户续约”相关实例 | 拥有成员状态的 DDD 大聚合 |
| **ExecutionPlan（执行计划）** | 具有名称和当前目的的 TaskSet 领域角色 | 目的是“确认续约风险与后续投入” | 另一张 `plans` 表、父 Task、目标达成证明 |
| **Kanban（看板）** | 由实例与执行段重建的只读投影 | 未开始、执行中、已暂停、已完成 | 独立事实表或任意拖拽写字段 |
| **BehaviorTimeSeries（行为时间序列）** | 从实例身份、模板归属、执行段和结果计算的读投影 | 复盘实例频次、首次开始间隔、投入分布 | 新事实、自动因果结论 |
| **候选解释** | 人可以确认、修订或否决的认识产物 | “可能适合双周常态化” | 已确认模板、周期计划或方向事实 |

### 2.2 易混词对照

| 词 A | 词 B | 区分方式 |
|---|---|---|
| 偶然性 | 一次性 | 偶然性描述来源；一次性只表示当前尚未确认第二个同类实例 |
| 可打断 | 可接续 | 前者决定是否允许暂停；后者决定暂停后能否追加新执行段 |
| 实际工作时长 | 执行自然跨度 | 前者求执行段时长之和；后者包含暂停和等待 |
| 期望结果 | 实际结果 | 前者在背景中，后者来自观察；二者不可互相覆盖 |
| 完成 | 结果达到期望 | 完成只是人确认这次工作结束 |
| 平级组合 | DDD Aggregate | 前者是业务归组；后者是一致性边界 |
| 时序关系 | 硬依赖 | `precedes` 默认只表达顺序，不自动阻止后项开始 |
| 模板默认值 | 实例本地值 | 实例化时复制；之后分别修订，模板修改不追溯 |

### 2.3 命令与查询也要说同一种语言

| 类型 | 示例 | 说明 |
|---|---|---|
| 捕获与修订 | `CaptureTaskInstance`、`ReviseTaskInstance` | 不要求先存在 Goal 或 TaskTemplate |
| 执行 | `StartTask`、`PauseTask`、`ResumeTask`、`CompleteTask` | 同一事务协调实例与执行段边界 |
| 时间补记 | `AddExecutionSegment` | `origin = manual`，不能伪装成实时计时 |
| 结果 | `RecordTaskResult` | 与 `CompleteTask` 是两个操作 |
| 类任务 | `ConfirmTaskTemplate`、`InstantiateTask`、`AssignTaskToTemplate` | 确认至少引用两个不同实例 |
| 组合 | `CreateTaskSet`、`AddTaskToSet`、`LinkPrecedence`、`NameExecutionPlan` | 不复制实例、不改变实例身份 |
| 查询 | `GetKanban`、`GetBehaviorTimeSeries` | 只读投影，不产生另一套事实 |

## 3. 子域划分示例

### 3.1 划分依据

不是按页面、数据库表或技术层划分，而是问：

1. 这组规则为什么变化？
2. 哪些事实必须一致地写入？
3. 哪部分能力形成当前产品的差异化价值？

### 3.2 四个子域

| 子域            | 类型       | 变化原因                | 输入                       | 输出                                               |
| ---           | ---      | ---                 | ---                      | ---                                              |
| **任务实例与执行事实** | 支撑子域     | 实际工作捕获、执行和结果记录方式变化  | 人的捕获、开始、暂停、完成、补记与结果录入    | TaskInstance、ExecutionSegment、TaskResult         |
| **类任务与类型演化**  | **核心子域** | 人如何识别重复工作、复用规约的方式变化 | 至少两个既有实例及人工同类确认          | TaskTemplate、实例模板归属、后续实例默认值                      |
| **工作组合与顺序**   | 支撑子域     | 实例归组、排序和计划解释方式变化    | 既有实例、成员选择与 `precedes` 关系 | TaskSet、Membership、TaskRelation、ExecutionPlan 角色 |
| **行为观察与复盘**   | **核心子域** | 观察口径、候选解释和复盘问题变化    | 上述三个子域的事实                | 行为时间序列、类任务／常态化／控制／组合候选                           |
|               |          |                     |                          |                                                  |

### 3.3 用 R1、R2 验证边界

1. R1、R2 可以各自执行和完成，此时不需要模板——说明实例事实可以独立存在。
2. 确认模板只改变知识层归属，不改写两个实例的执行段与结果——说明模板不应把全部实例装入自己的聚合。
3. 把 R2 加入计划，不改变 R2 的身份、执行历史或结果——说明 TaskSet 是平级组合，不是父任务。
4. 修改复盘日期范围，只改变读投影——说明统计不能回写执行事实。
5. “双周常态化”被否决，不影响任何实例——说明候选解释不是自动事实。

### 3.4 子域不等于四个限界上下文

当前实现仍是小型单体，不需要机械建立四个部署单元或四套数据库。初始代码落点可以是：

| 当前代码落点 | 主要职责 |
|---|---|
| `loom.task` | TaskInstance 捕获、修订、结果写入与仓储映射 |
| `loom.time` | Start／Pause／Resume／Complete 与 ExecutionSegment 的事务协调 |
| `loom.schema` | 共享词汇与数据结构，不承载业务流程 |
| `loom.db` | DDL 与数据库兜底约束 |
| 后续 `loom.template` | 类任务确认、实例化和归属写面 |
| 后续 `loom.composition` | TaskSet、Membership 与关系图写面 |
| 后续只读查询命名空间 | Kanban 与行为观察投影 |

只有当术语含义、规则变化原因或部署需求真正分裂时，才进一步形成独立限界上下文。**namespace 是边界纪律的落点，不是自动发现限界上下文的公式。**

## 4. ADR 示例一：ExecutionPlan 是否独立建聚合和表

### ADR-EX-001：ExecutionPlan 复用 TaskSet 身份

- **状态**：已决定（基于 DDD v0.2 的教学示例）
- **日期**：2026-11-25

**语境**

使用者需要把若干既有实例组成“企业客户续约”计划，观察顺序、完成数量和实际投入。计划不拥有成员执行事实，全部任务完成也不能证明续约目的实现。

**选项**

- **A. 独立 ExecutionPlan 聚合与 `plans` 表**：计划身份和生命周期独立，但需要维护 `plan/id → task-set/id` 映射；当前尚无独立计划生命周期需求。
- **B. TaskSet 的领域角色**：复用 `task-set/id`，只有名称与当前目的同时存在时承担 ExecutionPlan 角色；当前派生信息直接读取成员与关系。
- **C. 父 Task**：实现直观，但会制造父子层级，并把成员执行事实错误地归入父任务语义。

**决定**

采用 **B**。不创建独立 `plans` 表，不复制实例，不生成父 Task。

**理由**

当前需要的是“命名后的平级组合”，没有证据证明计划拥有独立状态机。复用 TaskSet 身份可以避免双写，并保持成员实例历史独立。

**后果**

- 正面：模型小；实例可保留独立身份；组合前后执行段与结果不变。
- 代价：未来若计划出现独立审批、发布或归档生命周期，需要新增 ADR 并迁移模型。
- 约束：计划目的达成不能由成员完成率自动推断。

**验证**

- 组合前后实例 ID、模板归属、执行段与结果完全不变。
- 同一实例在同一 TaskSet 中至多一条 Membership。
- 所有成员完成后，系统仍不自动写入“目的达成”。

## 5. ADR 示例二：TaskResult 是否立即升级为 Observation 聚合

### ADR-EX-002：当前只保存实例最新结果快照

- **状态**：已决定（基于 DDD v0.2 的教学示例）
- **日期**：2026-11-25

**语境**

R2 已记录“形成 3 项续约风险”，之后可能复查客户反馈。当前需求只要求保存实际结果、观察时间、录入时间和证据引用，尚未出现多次独立观测、驳回或确认历史。

**选项**

- **A. 当前 TaskResult 值对象**：作为实例内最新快照；结构简单，但旧快照会被新快照替换。
- **B. 独立 Observation 聚合**：保留多次观测及其生命周期；能表达复杂复查历史，但当前会增加身份、状态和查询成本。
- **C. 把结果追加到 ExecutionSegment**：实现少，但会混淆“时间怎样被使用”和“观察到了什么结果”。

**决定**

采用 **A**。`RecordTaskResult` 与 `CompleteTask` 保持独立；`observed-at` 与 `recorded-at` 分别保存，未知结果不由系统补造。

**理由**

当前没有多次独立观测的生命周期需求，不应为了假想复查流程提前建立 Observation 聚合。结果也不能依附执行段，因为完成后仍允许补记结果。

**后果**

- 正面：实例模型和结果录入界面保持简单；完成与结果有效不会混淆。
- 代价：重复录入只保留最新快照，不能回答完整观测历史。
- 演进触发器：出现多次独立观察、驳回、确认或证据版本需求时，新增 ADR 评估 Observation。

**验证**

- 可以先记录结果再完成，也可以完成后补记。
- 事后补记不会把 `recorded-at` 写成 `observed-at`。
- 实例完成不自动证明结果达到期望。
- 修改模板默认观测口径不会改写既有实例结果。

## 6. 留给所有者的练习

1. 换一个自己的真实任务，按 2.1 写出实例、背景、执行段和结果，标注每项“为什么不是另一个概念”。
2. 用“变化原因”重新检查四个子域，而不是按页面数量划域。
3. 从 `doc/decisions.md` 选择一个真正待决项，仿照本文写全选项技术后果、验证方法和未来推翻条件。
