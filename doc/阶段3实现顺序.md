## 实现顺序（10 步，每步一个 REPL 探针）

原则：**先打通地下管线，再开第一个阀门**。每步在 `user.clj` 用探针验收后再进下一步。

| # | 做什么 | 为什么在这个位置 | 验收探针 |
|---|---|---|---|
| 1 | `loom.db`：`datasource` / `ensure-schema!` / `snake-kebab-opts` | 一切写面的地基 | 内存库跑 `ensure-schema!`，6 张表（task_templates / tasks / execution_segments / task_sets / task_set_memberships / task_relations）都在 |
| 2 | `task->row` / `row->task` | 最纯粹的双语地带，无业务逻辑；转换一旦无损，后面只关心规则 | REPL roundtrip：领域值 → row → 领域值，过 `:task/instance` 校验且 `=` |
| 3 | `capture-task!` + `get-task` | 第一个真正的写路径；get-task 是后续一切函数的依赖 | 合法实例入库读回无损；`completed? true` 但 `completed-at nil` 被 malli `:fn` 拦下 |
| 4 | segment 映射 + `active-segment` 查询 | 映射同第 2 步；`active-segment` 是所有执行命令的守门员 | 空库返回 nil |
| 5 | `start-task!` | 第一个执行命令，跨表事务的最简形态 | 同实例 start 两次，第二次抛 `:time/conflict` |
| 6 | `pause-task!` / `resume-task!` | 都是"关一段、开一段"，骨架与第 5 步共享 | 不可打断实例 pause 被拒；`resumable? false` 实例 resume 被拒 |
| 7 | `complete-task!` | 有活跃段时拒绝；写 `completed=1` + `completed_at`，不推断结果 | 开着计时 complete 被拒；完成后可记录结果 |
| 8 | `add-execution-segment!` | 本阶段最难：手动区间的同实例不重叠判断（清单见下） | 补两段不重叠的 manual 段成功；重叠段被拒且已有段不变 |
| 9 | `record-task-result!` / `revise-task!` / `list-tasks` / `list-segments` | 收尾；查询是 Kanban / 统计投影的数据源 | `observed-at` 保留传入值、`recorded-at` 由函数产生，二者分开读回 |
| 10 | `user.clj` 三实例走查 + malli instrumentation | 任务卡第 6、7 条 | 走查单 7 条逐条过 |

第 5–7 步三个命令的骨架几乎相同（读任务 → 守门检查 → 写段 / 改任务），
建议先把 `start-task!` 在 REPL 里写顺，pause / resume 是它的变体，不要三个一起写。

## 三个贯穿要点

### 1. 映射层（第 2 步）值得单独一步

四类转换，roundtrip 无损后后面全部受益：

| 领域值 | 存储形态 | 说明 |
|---|---|---|
| UUID | TEXT | `str` / `UUID/fromString` |
| boolean | INTEGER 0/1 | 注意 `resumable` 允许 NULL（non-interruptible 时） |
| keyword 枚举 | 裸字符串 | `interruption-policy` ↔ `'interruptible'/'non-interruptible'`，`origin` ↔ `'timer'/'manual'` |
| `background` / `result-values` / `evidence-refs` | TEXT（EDN） | 写用 `pr-str`，读用 `clojure.edn/read-string`；**禁止**可执行的 `clojure.core/read-string` |

映射层只转换形状，不判断业务（completed 一致性、resumable 组合规则在领域侧已由 malli `:fn` 保证）。

### 2. L2 检查永远先于 L3 兜底存在

`start-task!` 先查 `active-segment` 再插入，不是为优雅：部分唯一索引 `uniq_active_timer`
撞上时 SQLite 抛的是原始约束错误，L2 先查才能翻译成可读的 `:time/conflict`。
L3 防"坏人直连写库"，L2 给合法调用者好错误。段不重叠、完成前无活跃段等跨行规则
DDL 表达不了（`loom.db` 注释已列明），只能在事务写面里查。

### 3. 事务边界跟着领域命令走，不跟着表走

`complete-task!` 同时动 `execution_segments`（确认无活跃段）和 `tasks`（写完成事实），
必须在同一个 `jdbc/with-transaction` 里——这正是 `loom.task` docstring 所说的
"Start / Pause / Resume / Complete 由 loom.time 的执行事务协调"。
反过来 `capture-task!` / `revise-task!` 不碰段表。

## 第 8 步检查清单：`add-execution-segment!`

按顺序检查，任一不过即拒绝并说明原因（ex-info 带 `:error/type`）：

1. **实例存在**：`get-task` 非空，否则 `:task/not-found`。
2. **实例未完成**：`completed = 0`，否则 `:time/already-completed`。
3. **时间合法**：`ended-at > started-at`，两个都是 epoch ms 整数
   （写入前用 `:execution/segment` 的 `:fn` 不变量语义显式校验；origin 固定 `:segment.origin/manual`）。
4. **同实例段不重叠**：设新段 `[s, e)`，库内已有段 `[s2, e2)`（`ended_at` 为 NULL 视为开区间，
   用足够大的上界代替）。存在任意一条满足以下两条件即重叠，拒绝 `:time/overlap`：
   - `s < coalesce(e2, MAX)`（新段开始早于已有段结束）
   - `s2 < e`（已有段开始早于新段结束）
   - 特别地，实例存在活跃段（`ended_at IS NULL`）时，任何 `s >= s2` 的新段都与之重叠。
5. **事务写入**：INSERT 新段；以上检查与写入在同一事务内。

参考（HoneySQL 风格，伪代码）：

```clojure
;; 守门查询：是否存在与新段重叠的段
[:select :id
 :from :execution-segments
 :where [:and [:= :task-id task-id]
              [:> :ended-at new-start]   ;; 已有段结束晚于新段开始；NULL 时此行不成立
              ...]]
```

注意"开区间参与比较"是这段逻辑最容易写错的地方，建议先写两个已知重叠 / 不重叠的
固定探针，再写边界探针（首尾相接 `e == s2` 不算重叠，半开区间语义）。
